# PORTX Architecture

PORTX gives a Unix-style shell on Windows (MSYS2, Git-for-Windows, Cygwin, WSL) transparent access to a curated set of Windows CLI tools. Each tool is a portable package; a PowerShell importer generates thin shell wrappers that `exec` the package's executable.

```
┌────────────┐    ┌─────────────────────┐    ┌──────────────────────┐
│ user shell │    │ PORTX wrapper       │    │ Windows executable   │
│ git status │──▶ │ wrappers/posix/git  │──▶ │ packages/.../git.exe │
└────────────┘    └─────────────────────┘    └──────────────────────┘
```

There is no runtime path-conversion layer. The wrapper detects the shell's drive-path convention (only to locate the package root), then `exec`s the Windows executable and passes arguments through unchanged; the tools handle path styles themselves.

## Package system

Each package is a directory under `packages/`:

```
packages/
  git-portable/
    cmd/git.exe ...          # executable(s) + bundled runtime
    portx.json               # manifest
  ripgrep/
    rg.exe
    portx.json
```

`portx.json`:

```json
{
  "name": "git-portable",
  "version": "2.51.0",
  "description": "...",
  "importType": "wrap",
  "bin": {
    "git": { "path": "cmd/git.exe", "description": "...", "tags": ["cli", "git", ...] }
  }
}
```

`bin.<tool>.path` is relative to the package directory and may be nested (`cmd/git.exe`, `mingw64/bin/git-lfs.exe`).

## Import types

`importType` selects how a package is exposed (schema `wrap | path | none | wrapAndPath`):

| Type | What the importer does | When to use |
|---|---|---|
| `wrap` | Generates a wrapper per `bin` entry that `exec`s that one executable. Package dir is NOT on PATH. | A tool (or a few) invoked by name. Most packages. |
| `path` | Adds the package dir (or its `packagePaths`) to PATH; no wrapper. | A bundle of many executables meant to be found together. |
| `wrapAndPath` | Both of the above. | Maximum compatibility. |
| `none` | Nothing imported (documentation package). | Reference-only. |

`wrap` is the controlled type — one name maps to one exact executable. `path` dumps a whole directory onto PATH and is the conflict-prone type (it can shadow, or be shadowed by, the host and other packages).

## Wrapper generation (ps/portx-import.ps1)

The importer scans `packages/`, reads each `portx.json`, and for `wrap`/`wrapAndPath` packages writes a bash wrapper (`wrappers/posix/<tool>`) and a cmd wrapper (`wrappers/windows/<tool>.cmd`).

Bash wrapper (Unix shells):

```bash
#!/bin/bash
# PORTX: <package>/<tool>
case "$(uname -sr)" in
    [Ll]inux*[Mm]icrosoft*) r="/mnt/c/App/PORTX" ;;             # WSL
    [Mm][Ii][Nn][Gg][Ww]*|[Mm][Ss][Yy][Ss]*) r="/c/App/PORTX" ;; # MSYS2 / Git-for-Windows
    [Cc][Yy][Gg][Ww][Ii][Nn]*) r="/cygdrive/c/App/PORTX" ;;      # Cygwin
    *) r="/c/App/PORTX" ;;
esac
args=("$@")
exec "$r/packages/<package>/<path>" "${args[@]}"
```

cmd wrapper (native cmd):

```cmd
@echo off
rem PORTX: <package>/<tool>
"C:\App\PORTX\packages\<package>\<path>" %*
```

The `case` block only picks the right drive-path prefix so the wrapper can locate the package across shells; it does not convert argument paths.

## PATH assembly

Two PORTX fragments extend PATH:

1. `path/portx_pkg_path` (generated by the importer) appends the PORTX root and the wrappers dir, and builds `PORTX_PACKAGES_PATH` from the `path`-type packages:

   ```bash
   export PATH="$PATH:$PORTX_ROOT:$PORTX_ROOT/wrappers/posix"
   export PORTX_PACKAGES_PATH="$PORTX_ROOT/packages/<pathpkg>/..."
   ```

2. The shell profile (`~/.bash_profile`) sources that file and appends the package paths:

   ```bash
   export PATH="$PATH:$PORTX_PACKAGES_PATH"
   ```

Both are **appends** (`$PATH:...`). The host shell's dirs (e.g. MSYS2's `/usr/bin`, `/mingw64/bin`) are already at the front, so on a name clash the host tool wins and the PORTX one is shadowed. To make a PORTX tool win, either avoid a name the host provides, or prepend the relevant fragment (safe for `wrappers/posix`; risky for `path`-type packages, which would shadow the host wholesale).

## Conflict model

- **One tool = one package.** Never define the same `bin` name in two packages — whichever imports last wins the wrapper (and re-importing one can silently clobber another's wrapper).
- **Prefer `wrap` over `path`.** `wrap` exposes exactly one controlled name; `path` exposes a whole directory and invites clashes.
- **Don't wrap what the host already provides** (ssh, tar, gzip, coreutils) unless you deliberately want the PORTX version to win — and then fix PATH order, don't add a wrapper that just loses.

## Package portability

A package is only as portable as its executable. A self-contained binary (static Go/Rust, or a tool carrying its own runtime) works on any host. A binary that loads DLLs from the host's runtime — e.g. a flat `git.exe` that finds `libcurl` on PATH — breaks when the host runtime changes.

`git-portable` is the reference for doing this right: it bundles git's full DLL closure — derived with a dependency tool (`objdump`, which also catches the **dynamically** loaded `libcurl` that a static import scan misses) — so it resolves every dependency from its own tree. It is verified self-contained by running git over https with the host runtime stripped from PATH (`PATH="/c/Windows/System32:/c/Windows"`); it still works, proving it uses no host DLLs. It therefore runs identically on MSYS2, Git-for-Windows, or Cygwin.
